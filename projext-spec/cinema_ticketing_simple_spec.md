一、轻量产品简报（Product Brief）——1页

1\. 一句话定位

面向［目标用户］的［什么类型购票］系统，帮助他们在［场景］下快速完成［选场次/选座/购票/取票］。

2\. 目标用户与核心痛点

**主要角色：**

* 购票用户：想快速查到场次、选座、支付、拿到票
* 运营/管理员：想上架场次、管理座位和订单、处理退改

**核心痛点：**

* 用户：场次信息分散、选座流程长、支付后取票麻烦
* 运营：场次和座位库存难管理、退改规则易出错

3\. 核心价值 / 差异化

* 用户侧：3步内完成购票（选场次→选座→支付），电子票即时到手
* 运营侧：可视化场次/座位管理，退改规则可配置

4\. MVP 范围

做什么（Must）

* 用户：浏览场次、选座、下单支付、查看电子票
* 管理端：创建场次、设置座位/票价、查看订单
* 基础规则：一人一票、支付超时释放座位、开场前可退

明确不做什么（Won't，本期）

* 不做会员积分、优惠券、拼团
* 不做线下核销硬件对接
* 不做多语言、多币种
* 不做复杂推荐算法

5\. 成功标准

* 核心购票流程可完整跑通，支付成功率 ≥ 95%（测试环境）
* 单场次 100 座位并发选座不超卖
* 用户从进入到拿到电子票 ≤ 3 分钟

6\. 主要风险

* 并发选座导致超卖 → 需座位锁定机制
* 支付回调丢失 → 需订单状态补偿
* 退改规则复杂 → MVP 先做固定规则

二、用户故事 / 任务清单（Backlog）

> 用 MoSCoW 排优先级，每条 Must 附验收标准（见第四部分）。  
> 建议放在 GitHub Issues / Trello / 飞书多维表格，此处为总览。

Must（必须做）

购票用户

* \[ ] **US-01** 作为用户，我能浏览场次列表（时间、地点、票价、余票），以便选择。
* \[ ] **US-02** 作为用户，我能查看场次详情和座位图，以便了解可选座位。
* \[ ] **US-03** 作为用户，我能选择座位并锁定，以便下单时不被人抢走。
* \[ ] **US-04** 作为用户，我能提交订单并在时限内支付，以便完成购票。
* \[ ] **US-05** 作为用户，我能查看我的电子票（二维码/票号），以便入场。
* \[ ] **US-06** 作为用户，我能在开场前申请退票，以便按规则退款。

运营/管理员

* \[ ] **US-07** 作为管理员，我能创建/编辑场次（时间、地点、票价），以便上架售票。
* \[ ] **US-08** 作为管理员，我能配置座位图和每区票价，以便控制库存。
* \[ ] **US-09** 作为管理员，我能查看订单列表和状态，以便处理异常。

系统规则

* \[ ] **US-10** 作为系统，支付超时（如15分钟）自动释放锁定座位。
* \[ ] **US-11** 作为系统，同一座位同一时刻只能被一个有效订单占用（防超卖）。

Should（应该做）

* \[ ] **US-12** 用户能按日期/地点筛选场次
* \[ ] **US-13** 管理员能导出订单报表
* \[ ] **US-14** 用户能收到购票成功通知（短信/邮件/站内）

Could（可做）

* \[ ] **US-15** 用户能收藏场次
* \[ ] **US-16** 管理员能配置不同退改规则

Won't（本期不做）

* 优惠券、积分、拼团、多语言、线下核销硬件

任务拆分示例（US-03 选座锁定）

* 前端：座位图渲染、可选/已售/锁定状态、点击选座
* 后端：座位锁定接口、锁定时长、释放逻辑
* 数据：座位状态表（可用/锁定/已售）、锁定过期时间
* 测试：并发选同一座位、锁定超时释放

关键流程标注（写在原型旁）

* **选座→锁定**：点击座位即锁定，倒计时15分钟
* **支付超时**：自动释放座位，订单变“已取消”
* **退票**：开场前可退，退款原路返回，座位释放
* **防超卖**：锁定即占位，支付成功转已售

四、验收标准（Acceptance Criteria）

> 每条用户故事用 \*\*Given / When / Then\*\* 写，开发完逐条勾选。

US-03 选座锁定

* Given 场次有可用座位  
When 用户点击某可用座位  
Then 该座位变为“已选/锁定”状态，并开始15分钟倒计时
* Given 座位已被他人锁定或已售  
When 用户点击该座位  
Then 提示“该座位不可选”，状态不变
* Given 两个用户同时选同一座位  
When 都提交锁定  
Then 仅一人成功，另一人收到“座位已被占用”

US-04 下单支付

* Given 用户已锁定座位且在倒计时内  
When 提交订单并支付成功  
Then 订单状态为“已支付”，座位转为“已售”，生成电子票
* Given 支付超时  
When 倒计时结束仍未支付  
Then 订单变“已取消”，座位释放为“可用”
* Given 支付回调丢失  
When 系统对账/补偿任务运行  
Then 订单状态与支付平台一致，不出现“已付款未出票”

US-05 电子票

* Given 订单已支付  
When 用户进入“我的电子票”  
Then 显示票号/二维码、场次、座位、入场须知
* Given 订单未支付或已取消  
When 用户查看电子票  
Then 不显示有效票，提示订单状态

US-06 退票

* Given 订单已支付且未开场  
When 用户申请退票  
Then 按规则退款，订单变“已退款”，座位释放
* Given 已开场  
When 用户申请退票  
Then 拒绝并提示“已开场不可退”

US-10 / US-11 防超卖与释放

* Given 座位处于锁定状态  
When 锁定超时  
Then 自动释放为可用，关联未支付订单取消
* Given 高并发选同一座位  
When 多个请求同时到达  
Then 数据库层面保证仅一个有效占用，不超卖

五、使用建议（个人团队）

1. **先写简报的 MVP 范围**，把 Won't 列清楚，防止膨胀。
2. **Backlog 只维护 Must**，Should/Could 放后面，做完再补。
3. **原型只画核心 6–9 个页面**，用便签标规则，不追求高保真。
4. **每条 Must 故事必须带验收标准**，这是自测和交付的底线。
5. **边做边补**：先跑通“浏览→选座→支付→电子票”主流程，再补退票、管理端报表。
6. **工具组合**：

   * 文档：Notion / 飞书文档 / 语雀（本文件）
   * 任务：GitHub Issues / Trello / 飞书多维表格（Backlog）
   * 原型：Figma / 即时设计 / Balsamiq
   * 验收：验收标准直接写在 Issue 里勾选
