MySQL 数据库，能在自己电脑上打开浏览器搜书、借书、还书就够了。

=== #2 [01:08 - 05:55] 版本控制 === [01:08]
你们三个人刚动手写代码，第一个要面对的问题就是怎么配合。你们分好了工，有人写借书，有人写还书，有人写页面。刚开始做课设，大家经常是写完一块就把整个项目打个压缩包，发到群里互相传，靠在文件名后面加
V1、V2、最终版来区分版本。传着传着肯定会乱。一旦发现最新的压缩包把代码改坏了，根本跑不起来，你想退回前面能跑的那一版，就只能去翻聊天记录一个一个找。就算翻到了，你也不知道中间这段时间大家改了什么，退回去会丢掉哪些代码。

想要解决这种混乱，就需要版本控制。版本控制指的是记录文件随时间发生的变化，方便以后查阅某次修改的细节，或者把整个项目退回到过去某个时间点的状态。现在最常用的版本控制工具是
Git。写代码的时候，你可以随时对比自己当前改了哪几行。等一个小功能或小步改动写妥了，再通过 Git
把这时整个项目的状态存成一条正式记录，并附上一句说明，这叫一次提交，也就是
Commit。历史上的每一次提交都会被保留下来，以后你随时能查看某两次提交之间具体改了什么，也可以把项目直接退回到过去某一次提交时的状态。用 Git
管理起来的整个项目文件夹叫一个仓库。在自己电脑上记好、提交之后，三个人要协作还得共用同一份代码，所以大家会在 GitHub
这类代码托管网站上放一个远程仓库。每个人从远程仓库拉取最新的代码，改完并提交以后，再推送回远程仓库，所有人的改动就都同步在上面了。

有了提交和远程仓库，三个人已经能用同一份代码同步干活了。但在实际开发里，很快会遇到另一个麻烦。假设你正在开发借书功能，需要几天才能写完，今天刚写了一半。如果你这时候提交并推送到远程仓库，没写完的半成品代码就会让整个程序跑不起来，队友拉下来以后也没法继续干活。可如果一直不提交，这几天的进度就没有版本记录，一旦电脑出问题或者自己改乱了就全丢了。

解决办法是利用 Git 的分支功能。每次提交，Git
都会把它们按先后顺序串成一条时间线，而分支本质上就是指向某条时间线上最新提交的一个轻量指针。项目默认有一条主分支，用来保存完整、能正常运行的代码。现在你可以从主分支上分出一条属于自己的分支，在自己的分支上想提交多少次都可以，别人看不到这条分支上的改动，可以继续在主分支上正常工作。借书功能在借书分支上开发，还书功能在还书分支上开发，等各自写完并测通，再合并回主分支。这样开发过程既安全，又互不干扰。

但借书功能写完，准备合并回主分支的时候，主分支上可能已经合进了还书功能。也就是说，开发历史从当初分叉的那个提交开始，分别走到了两个分支的末端。整合分支最常用的办法叫
Merge。Git
会把两个分支末端的最新快照，以及它们最近的共同祖先放在一起做一次三方合并，然后生成一个新的合并提交，把两条历史重新接到一起。如果两个分支修改的是不同的地方，Git
会自动把它们合到一起。但如果两个人在不同的分支里恰巧修改了同一个文件的同一部分，比如两个人都改了配置文件里设置最大借书天数的那一行，一边改成了 14
天，另一边改成了 30 天，Git 就没法替人决定留哪一边，这种情况叫合并冲突。这时候 Git
会暂停合并，把两边的修改都在文件里标出来，等你手动决定保留哪一方或者改写妥当，再重新提交，才算完成这次合并。

除了 Merge，整合分支还有第二种办法，叫 Rebase，中文常叫变基。Re 是重新，Base
是基底，意思就是把你当前分支的起点，从当初分叉的老位置重新换到目标分支的最新位置，再把你写的这些提交按顺序重新接上去。这样一来，虽然大家实际上是同时开发的，但提交历史看上去是一条干净的直线。

Merge 像是两条路在终点汇合，完整保留了历史上真实发生过的分叉，只是多出一个合并提交；Rebase
则是把你的改动重新接在最新主线后面，让历史记录保持一条直线，以后追查问题会更清爽。不过有一条重要准则要注意：已经推送到公共分支、被队友拉取过的提交，不要再做
Rebase，因为改写公共历史会让别人的本地仓库对不上号。实际团队开发里，平时在个人分支上常用 Rebase
保持历史整洁，而遇到大型需求、两边的冲突实在太多时，往往改用 Merge，在最后合并时一次性把冲突解决掉。靠仓库留住每次改动快照，靠分支把没写完的改动隔开，再靠
Merge 或 Rebase 把并行工作安全地收拢回主线，多人改同一份代码时的协作秩序就立住了。

=== #3 [05:55 - 09:45] 部署与扩容 === [05:55]
代码协作的问题理顺了，课设也顺利做完了。没想到学校图书馆觉得这个系统挺好用，打算拿去给全校正式用。可问题马上就来了：程序现在跑在你自己的笔记本上，一合上电脑，全校就借不了书。而且你在浏览器里访问的地址是
localhost，这个词指的就是本机，别的同学在自己电脑上输同样的地址，打开的还是他们自己的电脑，根本连不到你这里。

所以必须把这个程序搬出笔记本，放到一台常年开着、同学们都能连上的机器上。在网络服务里，这种常年通电联网、专门持续对外响应请求的计算机主机，就叫服务器。因为这套图书系统主要给校内师生用，学校很可能会把它部署在校园内网的服务器上，只允许校园网访问；如果希望校外也能打开，才需要给服务器配一个公网地址。不过现在多数团队都不会自己买机器建机房，更常见的做法是去阿里云、腾讯云这样的云厂商那里租一台云服务器。你租到手的机器，登录上去以后用起来就跟一台独立的远程电脑一样。

把程序搬上云服务器以后，图书馆正式用起来了。平时没什么压力，可到了开学第一周，全校学生都赶着上来借教材，这台服务器的 CPU
直接跑满，学生点开网页半天都打不开。遇到单台机器扛不住，通常有两条扩展路径。第一条叫垂直扩展，就是给这台服务器升级更高的配置，加 CPU
和内存，但这很快会碰到单机硬件上限，而且机器一旦出故障，整个系统还是会跟着停摆。更常见的是第二条，叫水平扩展，也就是多跑几份相同的后端程序一起来分担请求。同一份程序在操作系统里跑起来一份，就叫一个实例。平时口头上常把水平扩展说成加机器，但在云平台和后台操作时，真正增加的多数时候是实例数量。因为一台物理机上完全可以同时运行多个实例，你在云上新开的几台云服务器，在机房底层甚至可能落在同一台物理机上，只是各自切分出了独立的
CPU 和内存资源。所以更严谨地说，水平扩展是通过增加实例数量，让多份实例利用更多的计算资源同时处理请求。

可实例一多，外部流量怎么分发到各个实例上就成了问题。以前只有一个实例的时候，学校的域名通过 DNS
解析直接指向那台服务器就行。现在后面同时跑着好几个实例，而且它们可能分散在不同的服务器上，但对外的域名依然只有一个，就需要有一层专门的程序统一接收外部请求，再转发给后面的具体实例，这就叫反向代理，最常用的是
Nginx。在计算机网络里，代理分成正向代理和反向代理两类。正向代理部署在客户端这一侧，代表客户端向外访问网络，目标服务器不知道背后真正的客户端是谁；反向代理则部署在服务端这一侧，对外部的浏览器来说，反向代理自己就是那个服务器，它把后端多个实例的真实地址藏在后面，统一对外接收请求。

反向代理收到请求以后，还要决定把这一条请求交给后面的哪一个实例，这就是负载均衡。负载均衡的意思是把外部访问流量按照一定算法均匀分摊到一组功能相同的后端实例上，避免个别实例过载；同时通过定期发送健康检查探测，一旦发现某个实例没有回应，就自动把它从可用名单里摘掉，不再给它分流量。常用的分配规则包括按顺序轮流分配的轮询、给性能强的机器多分的加权轮询，以及谁当前处理的请求最少就分给谁的最少连接。如果反向代理从后面的实例拿不到正常回复，就会对外返回 502
错误；如果等待后端实例响应超时，就会返回 504 错误。

做到这一步，后端从一台笔记本搬到了云上。我们通过水平扩展增加实例来扛住计算并发，再用反向代理和负载均衡把外部流量均匀分摊到这些实例上。

=== #4 [09:45 - 18:00] 数据库与缓存 === [09:45]
可后端的并发撑住了，数据库又顶不住了。因为后端实例一多，同时涌进来的大量请求全往背后那唯一一台 MySQL 上压过去，MySQL 直接被高并发请求打满了。单台
MySQL 为什么扛不住这么高的并发？每一条 SQL 请求打进来，MySQL 都要走完一整套流程：服务层先要做连接管理、解析 SQL
语法，再由优化器算出执行计划，最后交给存储引擎去读写数据。虽然热点数据会尽量放进内存缓冲池，但没命中的数据依然要读磁盘；而且为了保住事务的持久性，每次写入提交都必须把日志刷到磁盘上；遇到多人同时改同一批记录，还得靠行锁来保证事务隔离，竞争同一行数据的请求就得排队。这些开销全压在一台机器的
CPU、内存和磁盘带宽上，请求量一旦超过单机上限，查询就会开始排队，响应变慢，甚至把连接占满。

既然一个后端程序可以跑多个实例来分摊压力，数据库可不可以也跑多个实例呢？可以，而且这正是数据库扩展最常见的一步。图书系统里，绝大部分请求是搜书、看详情这类只读操作，借书、还书这种改数据的写操作只占小部分。针对这种读多写少的业务，数据库常用的扩展方案叫主从复制，通常配合读写分离一起使用。团队会设置一台主库和一台或多台从库，所有改数据的写操作，比如借书和还书，全部交给主库执行。主库一边写，一边把数据变更日志同步给从库，让从库保持和主库一致；程序里的读操作就可以分散到多台从库上去查。这样一来，加从库就能把读能力拉上去，主库出故障时也有副本可以接替。

不过，只靠 MySQL
主从复制和读写分离往往还是不够，这里有两个现实限制。第一，主库把日志同步给从库需要时间，虽然平时只有几毫秒，但在写入压力大的时候可能会拉长，这就叫主从延迟。学生刚在主库还完最后一本书，紧接着刷新页面，查到了还没同步完的从库，就会看到库存还是 0。第二，每台从库本质上依然是磁盘型关系数据库，每次查书还是要做
SQL 解析和索引查找。开学季成千上万个学生反复点同一批热门教材，让多台磁盘数据库一遍遍重复去算同样的查询，成本太高，速度也还是不够快。

所以书名、简介这类老有人查、又不会每分钟都变的数据，就适合搬到更快的内存存储层里。实际项目里最常用来干这件事的工具是 Redis。Redis
是一个开源的内存型数据结构存储系统，它把数据主要保存在内存里，支持字符串、哈希、列表、集合等丰富的数据结构，同时也能通过快照或操作日志定期把数据持久化到磁盘上。正因为
Redis 直接读写内存，省掉了磁盘寻址和关系表解析的开销，单台机器每秒就能处理十万次以上的请求，响应时间通常在亚毫秒级。

正因为 Redis 是一个独立运行的高速内存型存储，它在这套系统里能承担两项核心职责。第一项也是最普遍的用法，是把它当做缓存放在 MySQL
前面。在计算机系统里，为了加速访问而用来临时保存热点数据副本的高速存储层，叫做缓存。把 Redis
当缓存来用时，最经典的读写配合方式叫旁路缓存。程序查书分成两步：先拿着书号去查 Redis，如果查到了，叫缓存命中，直接返回结果，根本不用打到
MySQL；如果没查到，叫缓存未命中，再去查 MySQL，查到以后顺手写一份回 Redis，同时设一个过期时间，防止旧数据一直占着内存。

不过，把缓存挡在数据库前面以后，最怕的是大量请求绕过缓存，一起砸到后面的 MySQL
上，常见的隐患有三种。第一种叫缓存击穿：热门数据缓存刚过期的那一瞬间，几千个学生同时来查这本考研教材，全都未命中，一窝蜂去查数据库。第二种叫缓存穿透：有人拿根本不存在的书号反复请求，这些书号缓存里永远没有，每一次请求都会穿过去打在数据库上。第三种叫缓存雪崩：比如程序提前把全馆书目放进缓存，过期时间又设成一模一样，到了整点全部同时失效，或者缓存服务本身挂掉了，所有查询一下子全涌向数据库。

防住这三种隐患，可以用下面几种办法：防热点过期瞬间并发回源，可以对重建操作加互斥锁，或者让极热的数据由后台异步刷新；防无效书号不断透传，可以在缓存里把查不到的空结果也短时间存下来，或者在前面加一层布隆过滤器拦截根本不存在的编号；防雪崩则要给过期时间加上随机抖动，把失效时间打散，必要时配合多级缓存和限流熔断保护数据库。另外，只要同时用了数据库和缓存，就会遇到数据一致性问题。比如学生刚还了一本书，MySQL
里的剩余数量已经加 1，可 Redis 里留的还是旧数字。一般的做法是在更新完 MySQL 之后，主动把对应的缓存删掉，让它失效，这样下一次再有读请求过来，在
Redis 里查不到就会自然打到 MySQL，把最新数字查出来再顺手放回缓存里，平时也会配合过期时间来兜底。

主从延迟和缓存一致性背后，有一条分布式存储的基本规律，就是常说的不可能三角。数据拆到多台机器上以后，高并发性能、低时延响应和数据绝对强一致很难同时占全，也就是
CAP
定理讲的一致性、可用性和节点断连时的容错能力不能兼得。放到图书系统里，如果非要让全网每一台从库、每一份缓存和主库在任何一毫秒都绝对一致，每次写入都得等全部机器同步锁死才返回，时延立刻拉高，吞吐性能也会掉下来。反过来，想要查书毫秒级返回、高并发下系统一直可用，就得允许缓存和从库存在短暂延迟，达成最终一致。常见的取舍是在查书名、看简介这些允许短暂延迟的地方用缓存和从库，保住低时延和高性能；而真正扣库存、办借书的那一步，还是直接走主库事务保证强一致。

Redis
在这里承担的第二项典型职责，是做所有后端实例共享的会话存储。前面我们把后端扩成了好几个实例，却会带来一个很具体的问题。以前只跑一个后端实例时，学生输入学号密码点登录，这个实例验证通过后，会在自己的内存里记下一条会话记录，里面写着学号、姓名和登录时间，同时生成一个随机的会话编号，通过
Cookie
发回给学生的浏览器。接下来学生搜书或者点借书，浏览器都会自动带着这个会话编号发出请求，这唯一的一个实例查一下自己的内存就知道是谁在操作。可现在前面摆了负载均衡，后面同时跑着多台实例，流程就断开了。学生先打开网页完成登录，如果负载均衡把这次登录请求打到了第一台实例上，那么这条登录记录就只记在了第一台实例自己的内存里；紧接着学生再点借书按钮，浏览器老老实实带着刚才拿到的会话编号发出第二个请求，这一次负载均衡却把请求分到了第二台实例上，第二台实例拿着编号去翻自己的内存，结果什么都查不到，只能把页面退回登录界面让他重新登录。

那怎么让第一台和第二台实例都能拿到这个学生的登录状态呢？办法就是把会话数据从每个后端实例自己的内存里搬出来，统一存进 Redis
这座所有实例都能访问的共享内存存储里。登录的时候，就算请求打到第一台实例，它也是把会话编号和对应的学号信息写进
Redis，再把编号返回给浏览器。下一秒学生点借书，请求被分到第二台实例，第二台实例从请求里取出同一个会话编号，直接去 Redis
里查，就能立刻拿到完整的登录状态和个人信息。这样一来，所有后端实例自己都不再保存用户状态，变成了无状态服务。无论后面开几台实例，或者哪台实例中途重启，学生都不会莫名其妙掉线，团队随时可以加减机器。

到这一步，数据库扩展先靠主从复制和读写分离把单库读写拆开，再引入 Redis 这类内存型数据结构存储，同时扛下热点数据缓存和共享会话存储两件大事，既把
MySQL 从高频重复查询里解放出来，也让后端实例真正实现了无状态扩展。

=== #5 [18:00 - 23:41] 代码上线 === [18:00]
机器和存储这边刚稳住，写代码的人这边又出了问题。有个同学改借书逻辑，写反了一个判断条件，改完直接推到主分支部署上线，结果全校半天谁都借不了书。

出了这事，就不能再允许谁想往主分支推代码就直接推。先把主分支设成保护分支，不允许任何人直接推送。以后谁要改代码，必须拉一条新分支，改完以后再申请把自己的分支合进主分支。在
GitHub 上，这种操作叫做提一个 Pull Request，简称 PR。不少公司为了把代码留在内部机房里，会私有部署开源的 GitLab 来管理仓库，在
GitLab 上同样的操作叫做提一个 Merge Request，简称 MR。把 PR 或 MR 提上去以后，不能自己直接合并，往往需要至少一位队友来做
Code Review，也就是代码评审。队友会逐行看一遍你的改动，检查逻辑有没有漏洞、边界条件有没有遗漏，确认没问题才同意合入。

可光靠人眼看代码难免会有疏漏，所以还需要一套自动化机制兜底。团队成员频繁把代码整合进主干，每次提交代码或者提起 PR、MR
时，都有系统自动执行编译、静态代码检查和自动化测试，这套开发实践叫
CI，也就是持续集成。只要其中任何一项检查没过，系统就直接卡住合并，把低级错误和明显漏洞拦在进主分支之前。

就算代码合进了主分支，也不能直接放给全校学生用。同一套系统要按用途部署出彼此隔离的环境，大多数公司实际上主要就分两套：一套是上线前用来做验证的预发布环境，另一套是真正面向用户提供服务的生产环境。新代码合入以后，先部署到预发布环境，这里的软硬件配置尽量和线上保持一致，团队用测试数据或隔离流量完整跑一遍，确认没问题再正式发布到生产环境。

有了评审、CI
和环境隔离，代码质量稳住了。但随着访问量继续涨，线上已经跑着十几个实例，每次更新版本又成了新麻烦。你得一台一台登录服务器去替换程序，又慢又容易漏。有一次，其中一台机器装的
Java 版本跟别的不一样，新代码在预发布环境跑得好好的，放到这台线上机器上却怎么都启动不了。另外，每次上线都是一次性把十几个实例全换掉，万一漏了一个
Bug，全校学生都会受影响。

想解决环境对不上的问题，可以把程序和它需要的运行环境一起打包，就像预先做好一套标准装修方案，里面封好了程序本身、特定版本的
Java、各种依赖库和配置文件。在容器技术里，这个只读的标准化静态打包文件叫做镜像。不管把同一个镜像拿到预发布环境还是生产环境的哪台服务器去启动，里面封好的运行环境一模一样，再也不会出现“我电脑上好好的，放到你那就报错”的情况。

镜像只是静态的模板文件，把它真正启动跑起来就是容器，目前最常用的工具是
Docker。容器利用操作系统内核提供的资源隔离和配额限制能力，为应用进程划出独立的运行空间。它就像在写字楼里隔出来的一间间独立办公室，一个容器里跑一个实例，和同一台机器上的其他程序互不干扰。你还能给每个容器规定资源上限，比如最多只准用 4G
内存，防止某一个程序把整台服务器的资源吃光。

以前每租一台云服务器，背后大多是一台虚拟机，也就是云厂商用虚拟化软件在一台大物理机上模拟出硬件并切分出来的一台台虚拟电脑。每台虚拟机就像一栋带全套水电的独栋房子，必须自带一整套完整的操作系统，占用资源多，开机也要几十秒甚至几分钟。而容器更像是直接住进写字楼的隔断间，它不带独立操作系统，直接和所在的宿主机共用同一个操作系统内核底座，只装程序自己需要的东西，所以容器特别轻，通常一两秒就能启动，一台服务器上能同时跑几十甚至上百个实例。

环境一致的问题解决了，接下来还要省掉手动一台台更新的麻烦，这就需要 CD，也就是持续交付和持续部署，指用自动化流水线接管打包、验证和上线发布。CD
分成两个层级：持续交付指的是主分支上的代码随时保持在可以安全发布的状态，系统自动完成打包镜像并部署到预发布环境做验证，只差最后一步由人点确认就能发布到生产环境；持续部署则更进一步，只要代码通过所有自动化测试，流水线就自动把它部署到生产环境，不需要人工再点确认。前面提
PR 或 MR 时自动编译测试的 CI，加上这里的自动打包部署 CD，合起来就是一条完整的 CI/CD 自动化流水线。

有了流水线以后，更新十几个实例不用再一台台手动操作了。但如果一次性全量替换，万一新版本里漏了一个
Bug，全校学生还是会同时受影响。所以往生产环境上线时，通常会做灰度发布：先只更新一两个实例，让负载均衡把一小部分请求切过去，让新版本在小范围真实流量下试跑一会儿，盯着监控里的报错率和响应速度，确认稳定了再一批批全量替换。一旦发现报错升高、指标异常或者出现非预期行为，出了
Bug 甚至服务崩溃，就立刻做回滚，把这一两个实例换回上一个版本的镜像，把影响控制在这几个实例和少部分用户之内。

整条交付链路跑通以后，先用保护分支、代码评审和 CI
保证合入主分支的代码质量，再用预发布环境把上线前的测试验收和生产环境隔离开，接着用容器和镜像保证程序在各台机器上的运行环境完全一致，最后靠 CD
流水线、灰度发布和回滚机制让新版本能自动化地安全上线，就算出了问题也能及时退回上一版。

=== #6 [23:41 - 29:07] 微服务 === [23:41]
就这样，系统在自己学校跑稳了，渐渐有了口碑，别的学校也陆续找过来说想用。慢慢地，它变成了几百所学校共用的大平台。往里加的功能越来越多，跨校借书、自习室座位预约、电子书、推荐功能全都加了进来，开发团队也从一开始的三个人扩大到了几十号人，可所有人改的还是同一个大程序。

把所有业务功能写在一个代码项目里，整体编译、整体打包、整体上线，这种架构叫单体架构。系统规模小的时候这样做结构简单，编译、调试都直接。但当团队和业务膨胀到一定程度，它会遇到三个很现实的难题。第一，几十号人的改动绑在一起上线，只要一个人带进了严重
Bug，所有人的改动都得跟着一起回滚。第二，故障没有隔离，座位预约里有个地方一直占着内存不释放，把整个进程撑崩溃了，结果连书都借不了。第三，资源没法按需扩展，开学季只有借书最忙，可因为所有功能全绑在一个包里，想扩容就得把平时并不忙的电子书和座位预约一块复制好几份，非常浪费机器。

于是团队按业务边界把大程序拆开，用户、馆藏、借阅、座位、通知、搜索，各自拆成一个独立的小程序，叫一个个服务。这种把单一应用拆成一组围绕业务能力构建的小型自治服务，每个服务有独立代码库和独立数据存储，可以独立开发、部署和独立扩缩容的架构风格，就叫微服务架构。拿用户和登录态这部分来说，前面在单体程序里，是由各个后端实例直接去
Redis
里读写会话。拆成微服务以后，用户信息、账号权限和登录会话就会被收进独立的用户服务或统一认证服务里管理。到了大公司，这一块往往还会独立成一套全公司所有业务共同依赖的基础用户与认证系统。

拆成微服务以后，每个团队自己上线自己的新版本，谁也不耽误谁。座位服务崩了，顶多约不了自习室，借书照常跑；开学借书忙的时候，单独给借阅服务多加实例就行，不用陪着别的功能一起扩容。

不过，拆成微服务也是有代价的。以前所有代码都在同一个进程里，借阅逻辑在借书前想查用户有没有欠费、还能借几本，或者查馆藏还有没有库存，直接在内存里调一个函数就行，只要几纳秒，而且几乎不会失灵。把服务拆开以后，各个服务跑在不同的机器上，原来的本地函数调用全变成了跨机器的网络请求，耗时一下子长到几毫秒。更重要的是，网络本质上是不可靠的，随时可能变慢、丢包，或者对面的机器突然宕机。

早在最开始做课设的时候，浏览器和后端之间就已经在跨网络发请求传数据了，当时用的是 HTTP 加 JSON。因为 JSON
是纯文本格式，人一眼能看懂，浏览器也原生支持，所以面向外部浏览器和手机 App
的接口，一般还会继续用它。但在微服务之间，把这套直接搬过来就不太够用了。程序要往网线上发数据，必须先把内存里的对象转成一串能传输的字节，这叫序列化；对面收到后再还原成内存里的对象，叫反序列化。JSON
就是一种文本序列化格式。可内部服务调用比外部请求密集得多，学生点一次借书，背后可能要连着调好几个服务，每次都把字段名当文本重复传一遍，连数字也要转成字符，流量一大既占带宽，解析又费
CPU。而且各个服务往往由不同团队、不同编程语言开发，如果只靠文档或口头约定 JSON
字段，只要有人随手改了个字段名或类型，另一边还没同步更新，上线就会直接报错崩溃。

所以服务内部通信通常会换用 RPC，也就是远程过程调用，并配合 IDL 和二进制协议一起使用。IDL
全称是接口描述语言，它独立于具体编程语言，专门用来把接口结构和字段规则定义清楚，比如 1 号字段代表书号，2
号字段代表借阅天数，每个字段是什么类型。通信两边还能直接从同一份 IDL 文件里生成出各自语言的接口代码。更重要的是，团队使用 IDL
时会遵守一套严格的兼容性规范，默认原则是字段只增不减，绝不修改或复用旧字段的编号，新增字段也尽量标成可选的 optional，避免随便加上强校验的
required
限制。这样一来，就算借阅服务新加了一个字段并先上线，另一边的馆藏服务暂时还没跟进，收到不认识的字段编号也会自动跳过，不会把服务跑挂。等对方需要用到这个新字段时，再拉取最新的
IDL 重新生成代码就行。

在传输格式上，IDL 通常会搭配二进制序列化协议来用，常见的有 Protobuf 和 Thrift。它们不传冗长的字段名，只按 IDL
约定传字段编号和紧凑的二进制字节流，体积小得多，解析也更快。引入从 IDL
生成出来的客户端代码以后，你在借阅服务里调用馆藏服务，写出来的代码跟调自己本地的函数几乎一模一样。怎么建连接、序列化、发请求、收响应和反序列化，全由像 gRPC
这样的 RPC 框架在底下替你处理好。

这样拆开以后，微服务用业务边界换来了独立发布、故障隔离和按需扩容，代价是把可靠的本地函数调用变成了不可靠的跨网络调用。面向外部终端时继续用 HTTP 加
JSON 保证通用和好调试，而在内部微服务之间，则靠 IDL、二进制序列化和 RPC 把跨服务调用重新拉回到高效、规范的契约轨道上。

=== #7 [29:07 - 32:55] 容器编排 === [29:07]
服务越拆越多，容器数量也跟着长起来。几十个服务，每个跑几十份，加起来就是几千个容器，分布在几百台物理机上。新容器该塞进哪台还有空闲资源的机器，没法靠人一个个挑；半夜三点有容器崩了或者机器坏了，也不能总靠人爬起来重启；开学前借阅服务要加实例，一台台手动操作早就忙不过来了。所以需要一个专门的系统来自动管理这些容器集群，这类系统叫容器编排系统，目前用得最多的是
Kubernetes，简称 K8s。它是一个用来自动化部署、扩缩容和管理容器化应用的开源平台。

K8s
最核心的设计思想叫声明式管理。区别于一条条教电脑先干嘛后干嘛的命令式操作，声明式管理是你只要交给系统一份清单，写清楚你期望系统达到的最终状态就行。比如借阅服务用哪个镜像、一直保持 50
份实例、每份配 2 核 4G 内存，剩下的全交给 K8s 的控制平面。它会持续盯着集群里的真实状态，一旦真实状态偏离清单，就自动出手把它拉回期望状态。

清单交上去以后，K8s 会自动查看哪几台机器还有空闲资源，把这 50
个容器安排上去跑起来，这叫调度。跑起来以后它还会持续做健康监控，半夜哪个容器崩了或者哪台物理机坏了，只要发现少了一份，只剩 49
份，它就会立刻在别的健康机器上补起一个，这叫自愈。开学前要扩容，把清单里的 50 改成 200 就行，甚至可以让它盯着 CPU
使用率自动扩缩容，忙的时候自己加，闲下来自己缩。换新版本的时候，把镜像版本改掉，K8s 会分批把旧容器替换成新容器，保证服务不断档，这叫滚动更新。

K8s 把几千个容器管起来以后，也带来了新问题。以前把程序固定装在几台物理机或虚拟机上，机器的 IP
地址很少变动，借阅服务只要把用户服务的地址写进配置文件里就能连上。可现在容器随时会被销毁、重建或者迁移到别的机器上，每逢扩缩容、发新版本或者崩溃重启，新容器都会分到一个全新的
IP 地址，在线实例的名单一直在变。

既然实例名单和 IP
地址一直在变，借阅服务就没法再把地址写死在配置文件里，否则只要后面有容器重启、迁移或者扩缩容，旧配置立刻就会失效，请求要么发到已经停掉的旧地址上报错，要么根本用不上新加进来的实例。解决办法是引入服务发现机制，让系统实时维护一份可用的服务地址目录，承担这份目录管理工作的组件就是服务注册中心。它的运转主要分三步：第一步是注册，每个实例一启动，就主动或者由平台代为向注册中心登记自己属于哪个服务、现在的地址是什么；第二步是保活检查，实例每隔几秒发一次心跳，或者接受健康探针检查，一旦超时没响应或者实例下线，注册中心就会把它从健康名单里剔除；第三步是查询和同步，借阅服务要调用用户服务时，不用记住任何具体
IP，只要按服务名去注册中心拿一份当前可用的实例名单缓存到本地，后续名单一有增减，注册中心还会及时推送更新。

常见的注册中心有 etcd、Nacos 和 Consul，而 K8s 内部自带的 Service 机制也能在集群内直接承担服务发现。注册中心和前面的 Redis
有一个共同点：它们都不直接实现借书、抢座这类业务功能，而是位于操作系统和业务程序之间，为所有服务提供通用底层支撑的基础软件，这一类软件统称中间件。

容器规模上千以后，K8s 用声明式编排管住了容器的生命周期，而服务注册中心则跟着动态变化的容器实例，实时维护出一张可靠的通信地址表。

=== #8 [32:55 - 36:40] 容错 === [32:55]
地址能动态找到了，可服务之间互相调用还会遇到另一个很棘手的故障。比如有一天，用户服务突然因为某个慢查询卡住了，响应变得极慢，借阅服务发过去的请求全都挂在那里等回复，等着请求越积越多，把借阅服务自己的线程和连接资源很快占满，借阅服务也跟着卡死；接着，调用借阅服务的上层服务也全被堵住，最后整个平台都打不开。

想防住这种连锁反应，得先拆解一次正常的 RPC
调用要经过哪些保护环节。调用方先从注册中心拿到地址列表，在本地用负载均衡算法挑出一个实例，把参数序列化成字节流。发请求的时候不能每次都临时新建网络连接，因为建立连接要来回握手确认，开销很大，必须从提前建好的连接池里复用连接。发出去以后也不能一直死等，必须设置一个合理的超时时间，等太久就直接放弃。要是挑中的单个实例刚好出故障，而且这个操作本身允许重复执行，还可以换一个实例重试几次。

超时和有限次数的重试能解决偶尔一两个实例抽风的问题，可如果整个用户服务都变慢了，借阅服务的每个请求都得等到超时才放弃，重试又会再多发几遍，排队的请求照样越积越多，最后把借阅服务自己也拖垮。这种由局部故障沿调用链逐级放大、最终导致整个系统瘫痪的现象，叫级联故障，也就是常说的雪崩效应。

要防止这种雪崩，通常会加上熔断机制，原理跟家里的保险丝一样，检测到下游撑不住就先主动跳闸断开。比如借阅服务发现调用用户服务的超时或失败比例在短时间内超过阈值，就会触发熔断，暂时断开这条调用链路。接下来一段时间里，请求不再真正发往用户服务，而是在本地立刻返回失败，或者改走提前准备好的降级逻辑，先保住借阅服务自己不被拖垮。降级在图书详情页里很常见，比如旁边的推荐服务出问题了，主页面干脆先不展示推荐列表，保证学生依然能正常看书、借书。过一段时间后，熔断器会进入半开状态，放少量请求过去试探一下。如果用户服务恢复正常，就重新闭合恢复调用；如果还在报错，就继续保持断开。

经常配合使用的还有舱壁隔离，做法是给不同的下游依赖各自划定独立的线程池或并发上限。这样就算推荐服务卡死、把自己的并发额度占满，借阅服务调用户服务和馆藏服务的资源依然不受影响。

除了前面说的序列化和 RPC
调用，找地址、负载均衡、连接池、超时、重试、熔断、隔离，这些事情每个微服务都要做，不可能让写业务的人各自从头写一遍。于是社区和基建团队把这些能力一起封装成现成的代码库，叫微服务框架。写业务的时候只要引入框架、配好规则，就能专心写借书还书的逻辑。因为框架是直接编译进程序里的代码库，所以通常按编程语言来选。比如这个图书平台，最早课设留下的老服务用
Java，后来新写的服务用 Go，搜索和推荐用 Python。各家公司在语言和框架选型上也有各自的习惯：字节后端主要用 Go，框架是 Kitex 和
Hertz；腾讯有 tRPC-Go；B 站有 Kratos；中小团队用 Go 常见的是 go-zero，或者 Gin 加 gRPC；阿里以 Java
为主，用的是 Dubbo 和 Spring Cloud；至于各种 AI 和算法服务，依然普遍使用 Python。

到了分布式环境里，系统容错有一个很直白的准则，就是永远不要相信你的任何上下游，因为网络和依赖随时都可能失灵。为了防住连锁反应，必须靠超时、受控重试、熔断降级和隔离把故障限制在局部，再用微服务框架把这些能力统一装进每个服务里。

=== #9 [36:40 - 40:30左右] 网关 === [36:40]
机房内部服务之间的通信和容错理顺了，我们再把视线拉回系统的最外层。现在来访问平台的，不只是浏览器网页，还有几百所学校的手机 App
和微信小程序。后端已经拆成了几十个微服务，每个服务都有自己的接口和职责。外部客户端既不可能、也不应该去记住几十个服务的内部地址，更不能把所有内部服务直接暴露在公网上。另外，几乎每个服务都要核对用户有没有登录，还要防着有人写脚本刷自习室座位，让几十个服务各自重复写一遍鉴权和防刷逻辑，既麻烦又容易漏。

回到最开始的概念，在计算机网络里，网关本来指的就是位于内部网络边界、负责与外界交互的出入口，就像家里的路由器站在家庭内网和互联网之间。前面单体阶段我们摆在最外面的反向代理，就已经兼任了简单的门户职责。到了微服务阶段，这个边界入口就正式演变成一个专门的组件，叫
API 网关，成为所有外部请求进入服务集群的统一总入口。

API 网关的职责可以分成两块：最基础的职能是路由，另一块可选的扩展职能是过滤。请求一进来，API
网关先做路由。它和前面讲的负载均衡器在技术实现上很像，但分工不同：负载均衡器是把同一类请求均匀分摊给一组相同的实例，而 API
网关主要负责根据请求里的特征，比如网址路径或请求头，把不同请求准确分发给内部对应的微服务。像抢座位的请求转给座位服务，借书请求转给借阅服务，具体的实例坐标依然去注册中心实时查询。如果有需要，网关还能在中间做一层协议转换，把外部网页和
App 发过来的 HTTP 加 JSON 请求，转换成内部微服务使用的 RPC 再往后发。

除了路由，API 网关还是天然的统一流量过滤器。所有外部流量都要从这里经过，所以 HTTPS
证书的统一加解密和登录状态的统一鉴权，都适合放在网关这一层一次搞定。前面单体阶段是由各个实例自己去查 Redis
里的会话，拆成微服务以后，就改成由网关拿着请求带过来的登录凭证，统一找认证服务或会话存储核验身份，查完再把确认过的用户信息安全地传给后面的借阅、座位等业务服务，几十个业务服务就不用各自重复写登录校验了。针对刷座位脚本的保护也放在这里，常见的做法是限流：当某个用户或者整个系统的访问速率超过承受上限时，直接在系统边界拦住多余流量，保护内部服务不被冲垮。当然，网关是所有流量的必经之地，不能把重业务逻辑塞进网关；而且网关自己也不能只跑单台，同样要部署多个实例，再由最外层的负载均衡把流量分摊到多台网关上，避免网关成为单点瓶颈。

到这里，集群内外的流量边界就分清楚了：外面从浏览器和手机 App 进来的请求，统一先经由 API
网关处理，做完鉴权、限流和路由再往里转发；真正进入集群以后，内部几十个微服务之间的互相调用、重试和熔断，再交给微服务框架去管。

=== #10 [约40:30 - 44:02] 消息队列 === [约40:30]
入口和调用链都打好以后，再把整个流程串起来看一遍。平台现在的业务已经比最初复杂了太多。最早做课设的时候，学生点一下借书，后端往数据库里改个库存、插一条记录就完事了。可现在服务了几百所学校以后，一次简单的借书或抢座，背后已经串起了一长串跨服务动作。比如一个学生在微信小程序上点借书，请求先过
API
网关核验身份，再进到借阅服务。借阅服务先调用户服务确认他没欠费、还能再借，再调馆藏服务扣减库存，把借书记录落库。到这一步，借书本身已经办完了，可紧接着业务还要干好几件事，比如通过微信小程序发一条借书通知、更新各学校的借阅统计报表，还要告诉推荐服务这个人刚借了什么书。

把这整条链路摆在面前，最直观的问题是借书记录落库以后，如果借阅服务同步挨个去调通知、统计和推荐，学生就得盯着加载界面干等，万一通知服务挂了，还会连累借书本身报错。在代码里直接起异步线程或者协程去后台发请求，主流程先给学生返回成功，确实能解决干等的问题，可放到多实例、随时会更新重启的生产环境里，进程内存里的异步协程会遇到三个实际问题：第一，任务全悬在容器自己的内存里，万一刚返回成功、请求还没发出去，这个容器恰巧崩溃或者发版替换了，这批通知和统计任务当场就会丢失；第二，遇到放座或开学季一秒涌进来几十万次请求，瞬间起几十万个协程，照样直接把下游的通知和统计服务打垮，甚至把借阅服务自己的内存也吃光；第三，借阅服务代码里写死了要调谁，以后再加个积分或打卡服务，借阅服务每次都得跟着改代码重新上线。

为了解决这种耦合、丢失和拥堵，标准做法是在服务之间引入一种专门用于异步通信和消息暂存的中间件，叫消息队列。它的底层模型正是操作系统课上学过的生产者消费者模型：发送消息的一方叫生产者，接收并处理消息的一方叫消费者。

引入消息队列以后，正好能把前面三个问题一并解决。第一个价值是可靠的异步：借书记录落库以后，借阅服务只要往消息队列里写一条“借书成功”的事件消息，马上就能给学生返回成功结果。和进程内起协程不同，消息队列独立跑在业务容器之外，哪怕下一秒借阅服务的容器重启甚至崩溃，已经写进去的消息依然安全存着，消费端照样能从队列里接着处理。第二个价值是削峰填谷：面对放座或开学季瞬间涌进来的几十万条通知和统计任务，先把这些消息一股脑写进消息队列里暂存起来，下游的通知和统计服务不用硬扛上游同时打过来的几十万个请求，只需要按照自己承受得住的速率平稳地一条条取出来处理，原本像尖刺一样的高峰流量就被队列拉平消化掉了。第三个价值，也是在大公司里作用非常大的一点，就是彻底解耦。通知、统计、推荐服务各自去订阅这一类事件消息，按自己的节奏取出来处理。把借书事件持续发进消息队列以后，这条消息流就相当于成了一套现成的底层基建。以后公司里其他团队新做一个积分服务、阅读打卡，或者数据团队要拿记录做分析，只要自己去接入并订阅这条已有的数据流就行，借阅服务一行代码都不用改，既不用配合对方排期开发，也不会被下游加进来任何额外的依赖和负担。

为了保证数据可靠，像 Kafka 和 RocketMQ
这样的主流消息队列，会把收到的消息持久化写到磁盘上，并在多台机器之间同步副本，就算坏掉一台机器消息也不会丢。不过在分布式网络里，想要绝对不丢消息，又要保证绝对只送一次，代价极高，所以绝大多数消息队列的默认保证是至少投递一次：遇到网络抖动、不确定对方收没收到时，宁可把同一条消息再送一遍，也绝不漏掉。这就要求消费方必须做到幂等。幂等在数学和计算机系统里，指的都是同一个操作执行一次和执行多次，最终对系统状态产生的结果完全一样。比如同一条借书或抢座成功的提醒，通知服务就算因为重试收到了两遍，也要靠去重记录保证只给学生发一条微信通知。

对于不需要当场拿到结果、或者存在突发洪峰的跨服务协作，消息队列通过可靠异步、削峰填谷和彻底解耦，把强依赖变成了有缓冲的松耦合联动。

=== #11 [44:02 - 46:31] 可观测性 === [44:02]
平台发展到这一步，组件越来越多，另一个头疼的问题也冒了出来：一旦线上出事，排查原因变得非常困难。有学校反馈学生借书偶尔会失败，你想想，一次借书要先过 API
网关，再经过借阅、用户、馆藏好几个服务，中间还进消息队列送到通知服务，成百上千台机器各自输出日志，根本没法像单机程序那样在自己电脑上打个断点看一眼。

把系统内部运行状态从外部透视出来的能力，叫做可观测性。它主要靠三根支柱撑起来，分别是聚合度量、事件日志和链路追踪。

第一根支柱是聚合度量，也就是系统监控。一方面，微服务框架和系统会自动上报流量大小、请求耗时和错误率这类通用指标；另一方面，写业务的研发也会主动在核心链路和关键节点上加上专门的监控打点和报错统计，比如扣减库存失败、调微信推送异常，只要走到关键分支就上报一次计数。系统把这些数据汇聚成实时监控图表，做灰度发布时盯的就是它们。人不可能 24
小时盯着屏幕，所以还要配报警规则，一旦错误率、延迟或者核心节点的报错指标超过阈值，系统就自动发消息，甚至打电话叫醒值班工程师，这种轮流值班响应的制度在公司里叫
on-call。

第二根支柱是事件日志。面对成百上千个随时可能销毁重建的容器，日志不能留在容器本地硬盘里，必须由日志采集组件实时收集到统一的日志存储和检索平台里，用来事后查清程序到底执行过什么代码、抛出了什么具体异常。

第三根支柱是分布式链路追踪，它用来回答某一次具体请求到底死在哪一环。请求一进 API 网关，网关就给它分配一个全局唯一的编号，比如叫 Trace
ID。微服务框架一路把这个编号塞进请求头里往下透传，经过的每一个服务、打印的每一行日志，甚至进出消息队列，全都带上同一个编号。等学校再反馈某次借书失败，只要拿着这个
Trace ID 在追踪平台上一搜，就能把这次请求跨越几十台机器的完整路径串成一条调用链，清楚看到每一步花了多少毫秒，报错到底出自哪一个服务。

聚合度量负责第一时间发现异常并触发报警，链路追踪负责把问题精确定位到具体哪一条服务，事件日志则负责还原当时的代码现场。这三根支柱配合起来，才让庞大的分布式集群从黑盒变透明。

=== #12 [46:31 - 结尾] 服务网格 === [46:31]
到这里，这个图书平台已经有几十个服务、三种编程语言了，靠微服务框架完全管得过来。可如果规模再往上翻，到了真正的大型互联网公司，上万个服务，Java、Go、Python、C++
全混在一起用，微服务框架自己就成了新的负担。服务发现、负载均衡、重试、熔断、链路加密这些通信逻辑，每种语言都得单独实现一遍，还要保证行为完全一致。更头疼的是升级，哪怕只是框架里修了一个安全漏洞，因为框架是编译在业务代码里的，上万个服务全得跟着重新编译、测试、上线，全部推完往往要好几个月。

为了彻底把通信治理和业务逻辑拆开，云原生技术栈里出现了一种叫 Service Mesh 的架构，中文叫服务网格，平时口头也常简称为
Mesh。它的做法是把服务间通信相关的发现、负载均衡、重试、熔断、安全加密的能力，从业务代码和语言框架里全部剥离出来，做成专门的独立代理进程。每个业务容器旁边都会紧贴着配一个这样的独立代理容器，共用同一份网络环境并跟着一起启停，业务服务所有进出的网络流量都先经过它来转发。这种给主容器旁挂一个伴生代理的做法就是
Sidecar 模式。当成千上万个业务容器都挂上自己的 Sidecar 并互相通信时，这些代理就在底层织成了一张覆盖全集群的通信网格，这也是 Mesh
这个名字的由来。

在 Service Mesh 的架构里，整套系统拆成两层来配合：所有紧贴着业务容器、直接经手每次真实请求并完成转发的 Sidecar
代理合在一起，叫数据面，也就是实际跑业务流量、干具体转发和容错动作的这一层；背后还有一套不直接碰具体请求、专门负责发号施令和统一下发规则的后台管理中心，叫控制面。平时要改超时时间、调限流阈值或者升级代理策略，只要在控制面改一次配置，它就会把新规则同步推送给全集群的
Sidecar 去执行，完全不用动业务代码，也不用管业务是用 Go、Java 还是 C++
写的。当然，像接口代码生成、语言内对象序列化这些跟编程语言强相关的事情，依然离不开框架，Service Mesh
主要接管的还是机房内部微服务之间的通信、调度和容错。

不过，Service Mesh 的代价同样不小。每一次服务调用都要先经过自己的 Sidecar，再经过对面的
Sidecar，等于凭空多了两层网络代理转发，请求延迟和全集群的
CPU、内存开销都会有一定的上升，底层网络排查和运维也需要专门的基础架构团队来维护。所以对我们这个几十个服务的图书平台来说，引入 Service Mesh
只会平白增加复杂度和运维成本；只有体量真的大到多语言框架推不动的大型团队，才值得付出这笔成本。技术选型不是越高级越好，架构演进的每一步，都是用当前承受得起的复杂度去换取当时真正需要的稳定性、扩展性和研发效率。

走到这里，前面提到的那些词也就不再是一串孤立的名词了。把代码写出来在自己电脑上跑通只是起点，真正决定一套系统能不能在线上活下来的，是在业务代码之外，用来对抗多人协作冲突、机器随时宕机、流量突发暴涨和依赖连环失灵的那一整套工程底座。不管你接下来是准备进大厂工作，还是正在做自己的项目，等用户量起来以后准备往线上扩容，背后要解的难题都是一样的。进了大厂以后，因为整套系统实在太庞大，你负责的往往只是其中的一小块业务，自己的笔记本根本装不下背后几十个依赖的服务和中间件，所以改完代码不再是本地点一下运行就算完，而是要走分支评审和
CI
检查，发到预发布环境跟上下游联调，再顺着监控指标、日志和链路追踪去定位线上问题。以后在面经、技术方案或者报错现场再碰到今天聊到的这些词，只要想一想它站在系统的哪一层、替系统解决了什么麻烦，整套工程逻辑就全通了。
