第一章：工程底座认知与分层架构基线（对应视频 #1 引言）
================================================================================
1.1 核心工程理念（Engineering Mindset）
- “写完本地可运行的 CRUD 功能”仅占真实企业级软件交付工作量的 10%。
- 剩余 90% 的核心工程复杂度源于四大生产级挑战：
  1. 多人并行协作：数十名工程师同时修改同一份代码库时的合并冲突与规范一致性；
  2. 高频持续交付：每日甚至每小时多次发布下的零停机保障与秒级故障回滚；
  3. 突发流量洪峰：业务高峰期（如学校开学周集中借还教材）下的高并发吞吐与存储抗压；
  4. 基础设施不可靠：云服务器宕机、网络抖动或依赖服务慢查询时的容灾与全链路排查。

1.2 三层架构代码职责铁律（单向依赖：Presentation -> Business Logic -> Data Access）
- 表现层（Presentation / Controller）：仅负责 HTTP 协议解析、请求参数格式校验（Zero-Trust Input Validation）、身份令牌提取与统一响应信封封装。严禁编写业务计算逻辑或拼接 SQL。
- 业务逻辑层（Business Logic / Service）：负责核心业务规则、领域状态机流转（如图书副本状态 `AVAILABLE -> RESERVED -> BORROWED -> MAINTENANCE/LOST`）与声明式事务边界控制。严禁将耗时的远程 RPC/HTTP 调用包裹在数据库长事务内。
- 数据访问层（Data Access / Repository）：负责 ORM 映射与持久化查询。严禁将数据库 Entity 直接暴露给表现层，必须转换为 DTO（Data Transfer Object）输出，防止敏感字段泄露。

1.3 架构演进量化触发阈值（防止过度设计）
- 当研发团队 <= 5 人、日活用户较低时，必须采用【模块化单体架构】，严禁提前拆分微服务；
- 架构演进的每一层引入，必须以“当前业务痛点已触及单机或单团队瓶颈”为前提。

第二章：版本控制与多人协作规范（对应视频 #2 版本控制）
================================================================================
2.1 仓库与分支策略
- 严禁通过压缩包或离线文件传输代码，所有代码统一托管至 Git 远程仓库（GitHub / 私有化 GitLab）。
- 主干分支（`main`）永远保持可随时发布状态；新功能开发必须拉取短生命周期特性分支（`feature/<ticket-id>-<desc>`，建议生命周期 <= 3 天），缺陷修复拉取 `hotfix/<ticket-id>-<desc>`。

2.2 Commit 规范与分支整合策略（Merge vs Rebase）
- 提交信息遵循 Conventional Commits 规范（如 `feat(borrow): add overdue fine calculation`）。
- 整合分支标准：
  * 个人私有分支同步主干最新进度时，优先使用 `git rebase` 保持提交历史呈干净直线，便于后续 `git bisect` 排查问题；
  * 公共分支（已推送并被他人拉取的分支）**严禁执行 Rebase**，防止改写公共历史导致团队仓库指针错乱；
  * 大型特性分支合并回主干或双方冲突密集时，使用 `git merge` 做三方合并，完整保留历史分叉与合并节点，并在本地人工解决冲突后通过完整测试再提交。

第三章：服务器部署、水平扩展与负载均衡（对应视频 #3 部署与扩容）
================================================================================
3.1 计算资源扩展策略
- 摆脱本地 `localhost` 运行模式，生产环境统一部署于云服务器（内网隔离部署或绑定公网网关）。
- 扩容优先级：优先采用**水平扩展（Horizontal Scaling）**增加无状态应用实例数量，而非单纯依赖存在物理上限与单点故障风险的垂直扩展（升级单机 CPU/内存）。

3.2 反向代理与负载均衡配置规范（Nginx）
- 反向代理位于服务端侧，隐藏后端真实实例 IP 地址，统一对外暴露单一域名入口。
- 负载均衡算法选型：
  * 机器配置均等：使用轮询（Round Robin）；
  * 机器硬件异构：使用加权轮询（Weighted Round Robin）；
  * 长短请求耗时不均：使用最少连接（Least Connections）。
- 健康检查与错误码治理：必须配置主动/被动健康检查探针，自动摘除无响应实例；规范监控网关层 `502 Bad Gateway`（后端实例无正常响应/进程崩溃）与 `504 Gateway Timeout`（后端处理超时）告警。

第四章：数据库扩展、Redis 缓存与分布式会话（对应视频 #4 数据库与缓存）
================================================================================
4.1 MySQL 主从复制与并发写入防超借规范
- 针对图书系统“读多写少”特征，采用一主多从架构实现读写分离：写操作（借书、还书）全部路由至主库，读操作（搜书、查详情）分发至从库。
- 并发防超借红线：扣减馆藏可用库存时，必须使用数据库乐观锁或条件更新（`UPDATE book_copies SET status = 'BORROWED', version = version + 1 WHERE id = ? AND status = 'AVAILABLE' AND version = ?`），严禁先查后改的非原子操作。
- 数据库版本迁移：所有 DDL 变更必须通过 Flyway 或 Liquibase 脚本管理（如 `V1__init.sql`），严禁手动在生产库直接修改表结构。

4.2 Redis 缓存架构与三大隐患防御（Cache-Aside 旁路缓存模式）
- 读链路：先查 Redis，命中直接返回；未命中则回源查 MySQL，并将结果写入 Redis 且**必须设置 TTL 过期时间**。
- 写链路（缓存一致性）：更新 MySQL 成功后，**主动删除（Delete）对应缓存 Key**（而非直接更新缓存，避免并发写覆盖脏数据），配合过期时间兜底。
- 三大缓存隐患防御标准：
  1. 缓存穿透（恶意查询不存在的 ISBN）：缓存短 TTL 空值（Null Object）+ 前置布隆过滤器（Bloom Filter）拦截；
  2. 缓存击穿（热点教材过期瞬间海量并发回源）：对缓存重建动作加分布式互斥锁（Mutex Lock），或对极热数据采用后台定时异步续期；
  3. 缓存雪崩（大量 Key 同时过期或缓存节点宕机）：基础 TTL 叠加随机抖动值（如 `3600s + random(0, 300s)`），并配置 Redis 高可用哨兵/集群模式与本地多级缓存降级。

4.3 CAP 定理取舍与共享会话（Stateless Service）
- CAP 取舍基线：普通书目检索允许毫秒级主从/缓存延迟，追求高可用与低时延（AP / 最终一致性）；核心借书扣减库存与罚金结算直连主库事务，保障强一致性（CP）。
- 共享会话规范：严禁在后端实例本地内存中保存用户登录 Session，必须统一托管至 Redis（或采用无状态 JWT），确保任意后端实例随时扩缩容或重启时用户登录态不丢失。

第五章：代码评审、容器化与 CI/CD 持续交付流水线（对应视频 #5 代码上线）
================================================================================
5.1 分支保护与质量门禁（CI）
- 开启 `main` 分支保护规则，禁止任何人员直接 `git push`，所有变更必须通过 Pull Request (PR) / Merge Request (MR) 提交。
- 自动化测试金字塔门禁（CI 阶段强制拦截）：
  * 单元测试（占比 70%）：Mock 外部依赖，核心业务逻辑与状态机覆盖率 >= 80%；
  * 集成测试（占比 20%）：使用 Testcontainers 启动真实容器化 MySQL/Redis 验证 SQL 与并发锁；
  * 契约与端到端冒烟（占比 10%）：OpenAPI 3.0 契约校验与核心借还书链路验证，任一环节失败直接阻断合并。

5.2 环境隔离与 Docker 容器化标准
- 严格隔离开发（Dev）、预发布（Staging，软硬件与配置对齐生产）与生产（Prod）三套环境。
- 镜像不可变性（Immutable Artifacts）：采用多阶段构建（Multi-stage Build）打包精简 Docker 镜像，打上唯一 Git Commit SHA 标签；同一镜像从 Staging 流转至 Prod，仅通过环境变量注入差异化配置，彻底消除环境不一致问题。
- 资源配额限制：每个容器必须显式声明 CPU 与 Memory 上限（如 `2C 4G`），防止单个容器内存泄漏拖垮整台宿主机。

5.3 持续部署（CD）、灰度发布与回滚红线
- 生产环境上线严禁一次性全量替换，必须执行**灰度发布（Canary Release）**：先切流 5% 至 1-2 个新版本实例，观测核心监控指标（错误率、P99 延迟）稳定后再分批放量。
- 一旦错误率或延迟突破阈值，立即触发一键回滚（切换回上一版本镜像标签），控制故障影响半径。

第六章：微服务拆分与跨服务通信契约规范（对应视频 #6 微服务）
================================================================================
6.1 拆分原则与数据隔离红线
- 当单体代码库引发“牵一发动全身的发布耦合、单模块内存泄漏拖垮全站、资源无法按需独立扩容”三大痛点时，按业务领域边界拆分为独立微服务（用户服务、馆藏服务、借阅服务、座位服务、通知服务、搜索服务）。
- **数据隔离红线**：每个微服务必须拥有独立的数据存储实例/Schema，**严禁跨服务直连对方的数据库表**，所有跨领域数据访问必须通过服务接口或事件流完成。
- 分布式事务红线：跨服务写操作（如借书扣库存 + 记账）优先采用“本地消息表 + 消息队列 + 消费端幂等”实现最终一致性，禁止滥用重型分布式强事务（2PC/XA）。

6.2 通信协议选型与 IDL 演进规范
- 南北向流量（外部浏览器、App、小程序 -> 网关）：采用 HTTP/1.1 或 HTTP/2 + JSON 文本格式，兼顾可读性与跨端调试便利。
- 东西向流量（内部微服务之间高频调用）：统一采用高性能 RPC 框架（如 gRPC / Kitex / Dubbo）+ 强类型 IDL（接口描述语言）+ 二进制序列化协议（Protobuf / Thrift）。
- **IDL 向后兼容性铁律**：
  1. 字段编号（Tag Number）全局唯一，**只增不减，严禁修改或复用已废弃字段的编号**；
  2. 新增字段一律定义为 `optional`，禁止添加强制校验的 `required` 约束，确保新旧版本服务灰度共存期间反序列化零报错。

第七章：Kubernetes 容器编排与服务注册发现（对应视频 #7 容器编排）
================================================================================
7.1 K8s 声明式编排与高可用探针基线
- 全面采用 Kubernetes（K8s）YAML 清单进行声明式资源管理，利用控制平面实现自动调度、节点故障自愈（Self-Healing）、基于 CPU/QPS 指标的水平自动扩缩容（HPA）以及零中断滚动更新（Rolling Update）。
- **生产容器探针与优雅停机基线（强制要求）**：
  * 必须同时配置 `livenessProbe`（存活探针，僵死自动重启）与 `readinessProbe`（就绪探针，未完成连接池预热前禁止接入外部流量）；
  * 必须实现 `SIGTERM` 优雅停机（Graceful Shutdown），收到终止信号后先摘除负载均衡流量，等待正在执行的借还书事务处理完毕后再关闭进程。

7.2 动态 IP 环境下的服务注册与发现
- 鉴于容器重启与扩缩容导致 IP 动态变化，严禁在配置文件中硬编码下游服务 IP。
- 统一接入服务注册中心（Nacos / etcd / Consul 或 K8s 原生 Service）：实例启动自动注册、定期心跳保活剔除失联节点、调用方按服务名拉取并本地缓存健康实例列表。

第八章：分布式容错与防级联雪崩规范（对应视频 #8 容错）
================================================================================
8.1 零信任上下游原则与五大容错机制
- 核心原则：**永远不要相信任何上下游依赖，网络与下游服务随时可能变慢或失灵**。
- 标准防雪崩组合拳：
  1. 连接池复用：禁止每次 RPC 临时建连，统一配置长连接池与最大连接数上限；
  2. 严格超时控制（Timeout）：所有跨网络调用必须设置显式超时时间，严禁无限期阻塞等待；
  3. 受控重试（Bounded Retry）：仅对具备天然幂等性（或已携带幂等键）的读/写操作开启有限次数重试（如最多 2 次），严禁在全链路每一层叠加无限制重试引发重试风暴；
  4. 熔断器（Circuit Breaker）：当下游错误率或超时比例超过阈值时自动跳闸进入 `Open` 状态，本地快速失败（Fail-Fast），冷却期后进入 `Half-Open` 状态放行少量探针请求试探恢复；
  5. 降级与舱壁隔离（Fallback & Bulkhead）：非核心依赖（如推荐图书列表）异常时执行静态兜底降级，保障核心借还书主流程可用；为不同下游依赖分配独立线程池或信号量配额，防止单一慢服务耗尽全局线程资源。

第九章：API 网关与边界流量治理规范（对应视频 #9 网关）
================================================================================
9.1 统一入口职责边界
- API 网关作为集群外部流量的唯一统一入口，负责按请求路径/Header 路由至后端微服务，必要时完成外部 HTTP/JSON 到内部 RPC 协议的转换。
- **网关轻量红线**：严禁在 API 网关中编写重型业务逻辑或直接访问业务数据库；网关自身必须多实例无状态部署，前端挂载外层负载均衡器消除单点故障。

9.2 统一鉴权与边界限流
- 统一身份认证：在网关层集中完成 HTTPS 卸载与登录凭证校验（推荐结合 JWT 公钥本地验签 + Redis 黑名单机制），校验通过后将标准化的用户身份上下文（如 `X-User-Id`、`X-User-Role`）透传至内部微服务。
- 边界限流防刷：针对高频抢座、批量爬书等异常流量，在网关层按用户 ID、IP 或接口维度配置令牌桶/漏桶限流规则，直接于系统边界拦截超额流量。

第十章：消息队列异步解耦与消费端幂等规范（对应视频 #10 消息队列）
================================================================================
10.1 异步通信三大核心场景
- 禁止在主业务接口（如借书落库）中同步串行调用通知推送、统计报表、积分计算等非核心下游，亦禁止使用进程内内存协程（容器崩溃或发版会丢失内存任务）。
- 引入持久化消息队列（Kafka / RocketMQ）实现三大工程价值：
  1. 可靠异步：事件落盘多副本持久化，业务容器重启不丢消息；
  2. 削峰填谷：平滑吸收开学季或抢座瞬间的几十万级并发尖刺，保护下游数据库按稳态速率消费；
  3. 彻底解耦：核心借阅服务仅负责发布标准领域事件，新增积分、打卡、数仓分析等下游团队直接订阅消息流即可，上游零代码改动。

10.2 At-Least-Once 投递保证与消费端幂等铁律
- 主流消息队列默认提供 **At-Least-Once（至少投递一次）** 语义，网络抖动时必然存在消息重复投递。
- **消费端幂等红线**：所有消息消费者必须具备严格的幂等处理能力（利用全局唯一 `eventId` 配合数据库唯一索引或 Redis `SETNX` 去重表），确保同一条借书事件被消费 1 次与消费 N 次对系统状态与用户通知的结果完全一致。

================================================================================
第十一章：全链路可观测性与 On-Call 运维规范（对应视频 #11 可观测性）
================================================================================
11.1 可观测性三大支柱
1. 聚合度量（Metrics）：自动采集请求速率（Rate）、错误率（Errors）、响应延迟分位数（P50/P95/P99）及自定义核心业务打点（如库存扣减失败次数），实时聚合监控大盘。
2. 集中式事件日志（Logs）：严禁将日志仅留存在易失的容器本地磁盘，所有实例统一输出结构化 JSON 日志并实时采集至集中检索平台。
3. 分布式链路追踪（Distributed Tracing）：请求进入 API 网关瞬间生成全局唯一 `Trace ID`，通过 HTTP Header / RPC Metadata / MQ 消息属性全链路透传，并自动注入每一行日志，实现跨数十台微服务的调用耗时与故障节点秒级定位。

11.2 分级告警与无指责复盘
- 建立 On-Call 轮值响应机制：P0/P1 级核心告警（如借书接口错误率 > 1% 或 P99 延迟突增）自动触发即时通讯与电话外呼，优先执行回滚止损，故障恢复后输出无指责复盘报告（Blameless Postmortem）并沉淀为自动化防线。

================================================================================
第十二章：服务网格（Service Mesh）演进边界与终极选型准则（对应视频 #12 服务网格）
================================================================================
12.1 架构原理与适用边界
- 原理：通过 Sidecar（伴生代理容器）模式将数据面（流量转发、重试、熔断、mTLS 加密）与控制面（规则统一下发）分离，将通信治理能力从多语言业务框架（Java/Go/Python/C++）中彻底剥离。
- **引入红线（防止盲目引入）**：Service Mesh 会引入双层 Sidecar 网络转发延迟、额外的集群 CPU/内存开销以及高昂的底层网络运维复杂度。**仅当企业服务规模达到数千至上万个、且存在多语言异构框架升级推进困难时方可执行演进**；几十至数百个服务的常规业务系统应坚持使用成熟微服务 SDK 框架。

12.2 全架构演进终极准则
- **架构设计不是技术名词的堆砌，而是用当前团队与基础设施承受得起的复杂度，精准换取当下业务真正需要的稳定性、扩展性与研发效率。**
